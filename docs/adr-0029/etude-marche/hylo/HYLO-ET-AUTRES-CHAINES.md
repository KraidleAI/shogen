## 1. Hylo (Solana)

### 1.1 Ce que fait le protocole [lu]

- **Idée** : séparer une garantie volatile en deux : un jeton à levier (xAsset) et une unité stable virtuelle (vUSD). Page d'introduction : “a highly decentralized stablecoin with no single point of failure” (`pages/hylodocs-introduction.md`, https://docs.hylo.so/introduction). La même page revendique : “No fund manager, no third-party trading dependencies.” Cette phrase est à lire avec §1.3 : Hylo dépend de Pyth pour le prix et de Sanctum pour les taux des LST [lu]. La phrase vise sans doute la gestion et les contreparties de négociation, pas les oracles **[inféré]**.
- **Chaîne** : Solana (page d'adresses `hylodocs-security-onchain-addresses.md` : programmes Exchange `HYEXCHtH…` et Stability Pool `HysTabVU…`, adresses complètes dans la page) [lu].
- **Produits** (docs `hylodocs-product-guide-*.md`) : hyUSD (stablecoin), eHYUSD (jeton de l'Earn Pool, rendement), xSOL / xBTC / xHYPE (levier sans liquidation), hyloSOL et hyloSOL+ (LST) ; xActions, xMatières premières et xRendement annoncés comme à venir (“Coming soon.”) [lu].
- **Mécanisme** : chaque pool de garantie a son propre ratio de collatéralisation (CR), cible 150 %, six zones (≥175 % achat 2 ; 165–175 % achat 1 ; 135–165 % neutre ; 120–135 % vente 1 ; 100–120 % vente 2 ; <100 % déstabilisé) (`hylodocs-protocol-overview-risk-management.md`). Le rééquilibrage ouvre des routes d'échange avec USDC à un prix égal au prix d'oracle corrigé d'un écart en pourcentage qui varie avec le CR selon un barème fixe ; en dessous de 100 %, l'Earn Pool brûle du hyUSD pour absorber le trou (`hylodocs-technical-addendum-additional-risk-management.md`) [lu].
- **Garanties** : pool SOL (jitoSOL, hyloSOL), pool BTC (cbBTC), pool HYPE (HYPE sur Solana), pool USDC sans levier (`hylodocs-protocol-overview-multi-asset-architecture.md`) [lu]. Les frais USDC sont de 0 % à la création et 0,2 % au rachat (même page) [lu].
- **Ce que le SDK ajoute** : le module de flux Pyth du SDK (`sdk-hylo-core-src-pyth-feeds.rs`) définit aussi des flux pour **ETH/USD (WETH), ZEC/USD, ONYC/USD et PST/USDC**, que les pages de docs lues ne présentent pas comme produits [lu pour le code, **[abs]** pour l'état en production].

### 1.3 D'où vient le prix : la chaîne de dépendances [lu sauf mention]

**Qui fournit le prix, actif par actif** (`hylodocs-technical-addendum-hylo-equations.md`, section Price Oracles ; `hylodocs-protocol-overview-multi-asset-architecture.md`) :

| Actif | Source du prix | Citation |
|---|---|---|
| SOL (via les LST) | taux du pool de mise en jeu via le programme Sanctum, puis Pyth SOL/USD | “The Pyth SOL/USD oracle then converts SOL to USD.” (multi-asset) |
| cbBTC | Pyth BTC/USD (le BTC enveloppé est donc valorisé par le prix du BTC, pas par un prix cbBTC) | “Pyth BTC/USD price oracle.” (multi-asset) |
| HYPE | Pyth HYPE/USD | “Pyth HYPE/USD price oracle” (équations) |
| USDC | valorisé 1 $ par construction ; Pyth USDC/USD ne sert que de garde-fou | “Pyth USDC/USD price oracle, used as a par check only” (équations) |

**Combien de sources** : une, par actif [lu pour les docs ; lecture **partielle** du SDK]. Les pages de docs ne nomment que Pyth. Dans les sept fichiers du module `hylo-core` que j'ai copiés (`error`, `lib`, `par_tolerance`, `pyth/feeds`, `pyth/mod`, `pyth/oracle`, `solana_clock`), seul Pyth apparaît ; `lib.rs` déclare une vingtaine d'autres modules (`exchange_context`, `rebalance`, …) que je n'ai **pas** lus. La politique d'ajout d'actifs liste pourtant, comme critère, un oracle avec “Multiple sources available” (`hylodocs-technical-addendum-value-at-risk-analysis.md`) : cela peut désigner les éditeurs multiples de Pyth, pas des oracles distincts **[inféré]** ; la page ne le précise pas **[abs]**.

**Comment le prix est lu** (SDK `sdk-hylo-core-src-pyth-oracle.rs`, fonction `query_pyth_oracle`) [lu] :
1. le compte de prix doit avoir le niveau de vérification `Full` (erreur de message “Oracle price update is not fully verified”) ;
2. l'heure de publication est acceptée si `publish_time + intervalle >= heure_chaîne` (ligne 132) ; **seule cette borne est testée** : une heure de publication en avance sur l'horloge Solana passe, ce qui correspond à la remédiation d'OtterSec ADV-03 contre la dérive d'horloge, et ACC-L7 (p. 49) décrit le même test. L'intervalle fermé `[heure_chaîne − intervalle, heure_chaîne]` n'est que dans le commentaire du code (lignes 119–120) ;
3. le slot de publication ne doit pas être plus vieux que l'intervalle converti en slots de 200 ms (ligne 146–158) ;
4. le prix doit être positif, exposant entre −2 et −9 ;
5. le rapport `conf / prix` doit rester sous la tolérance ; **bornes codées : intervalle de 1 à 60 secondes, tolérance de confiance jusqu'à 5 %** (`MAX_CONF_TOLERANCE = 50_000_000` en 9 décimales) ;
6. pour un stablecoin, l'intervalle est divisé par 4 (`ORACLE_DIVISOR`) ;
7. le prix devient une **fourchette** `(prix − conf, prix + conf)` ; le commentaire du code précise “Use lower in minting, higher in redeeming”. La doc illustre ce choix par une image dont le texte alternatif est “Collateral Rebalancing Oracle Pricing (Pyth plus or minus CI)” (`hylodocs-protocol-overview-collateral-rebalancing.md`, légende d'image).

**Contrôle de parité USDC** (`sdk-hylo-core-src-par_tolerance.rs`) : les routes USDC exigent `|1 − spot USDC| ≤ tolérance`, tolérance configurable entre 0,00001 et 0,001 (`MIN 10_000`, `MAX 1_000_000` en 9 décimales). Docs : “USDC routes are only available while the Pyth USDC/USD price stays within a small configured tolerance of $1.” (multi-asset) [lu]. **Le contrôle utilise le même fournisseur que le reste** : un décrochage de Pyth sur USDC bloque les routes USDC, il n'est pas confirmé par une autre source [lu, inféré pour la conséquence].

**Si une source s'arrête ou diverge** [lu pour les codes, inféré pour le comportement global] :
- prix trop ancien : erreur “Oracle did not yield a price within the configured age window.” (`sdk-hylo-core-src-error.rs`) ;
- intervalle de confiance trop large : “Oracle confidence interval is too wide.” (même fichier) ;
- l'audit Accretion de juillet 2026 décrit l'effet : “an oracle becomes rejected by the protocol due to quoting too wide or being stale” et note que cela “can happen in a crash” (`audit-Accretion-HyloV2-July2026.txt`, ACC-L1, p. 37) ; les instructions de règlement échouent mais la sortie de l'Earn Pool restait possible au NAV d'avant règlement (corrigé, FIXED) ;
- les chemins de rééquilibrage utilisaient un intervalle codé en dur de **1 seconde** (ACC-L7, BASSE, corrigé, p. 49) : l'audit parle de “liveness risk on the exact paths used for rebalancing” ;
- **aucune divergence entre deux sources ne peut survenir, puisqu'il n'y en a qu'une** ; le seul contrôle de dispersion du code lu est le rapport entre l'intervalle de confiance et le prix (le fichier `pyth-oracle.rs` ne contient aucune occurrence de `ema` ; OtterSec ADV-01 a remplacé l'EMA par le spot) [lu, inféré].

**Amont de Pyth** (pages `pyth-*.txt`) :
- Pyth Core : “120+ first-party publishers including major exchanges, trading firms, and market makers” (`pyth-core.txt`, présentation générale) ; le nombre d'éditeurs **par flux** (SOL, BTC, HYPE, USDC) n'est pas sur les pages lues **[abs]** ;
- le prix agrégé est la **médiane** des prix des éditeurs, la confiance est l'écart interquartile ; sous `min_pub` éditeurs, plus aucun nouvel agrégat n'est produit et les champs sont reportés (`pyth-pro-data.txt`) [lu] ;
- **Pythnet est en cours d'arrêt** : “Pythnet is shutting down; Pyth Pro documents the current architecture” (`pyth-aggregation.txt`) ;
- depuis le **2026-08-26 16:00 UTC**, Pyth Core est signé par **cinq routeurs Pyth Pro**, quorum **3/5** (contre 13/19 gardiens Wormhole avant) (`pyth-upg-how.txt`, tableau de comparaison) : “The network consists of five independently operated routers.” ; mais “Douro Labs operates the relayer service for the Pyth Pro network.” (`pyth-pro-how.txt`) : les cinq routeurs semblent donc consommer le même flux de la même file de messages [lu pour les deux pages, inféré pour la conclusion] ;
- selon la page Solana de la mise à niveau, les programmes de réception changent : “hardcodes the Pyth program addresses” (`pyth-upg-solana.txt`), et les comptes push par flux changent aussi ; **mais** `pyth-upg-contracts.txt` écrit pour le 2026-08-26 “You kept your address, and your feed IDs didn't change” (sauf sur Sui) : les deux pages Pyth ne disent pas la même chose (§5), et la table des comptes, rendue en JavaScript, est absente de la copie. **Le workspace du SDK Hylo épingle `pyth-solana-receiver-sdk = { version = "=1.2.0", features = ["pro-compatible"] }`** (`sdk-Cargo.toml`) ; la version 2.6.2 du crate `hylo-core` a été publiée le **2026-09-30** (`crates-hylo-core.json`) [lu]. ### 1.7 Ce que Shōgen pourrait lui apporter, concrètement **[inféré]**

Vocabulaire repris de `SYNTHESE-CROISEMENT.md` : R1 = écart entre sources d'un même actif (leave-one-out), R2 = carte des racines communes, S2-bis = BTC, ETH, USDC, USDT.

1. **Une série de comparaison sur des places hors Pyth, pour deux des actifs de Hylo (recouvrement avec les éditeurs de Pyth non mesuré).** D'après les docs, Hylo lit Pyth BTC/USD et USDC/USD ; S2-bis mesure déjà ces deux actifs. ETH/USD n'est que défini dans le SDK (associé à WETH sous `#[cfg(feature = "offchain")]`, `feeds.rs` l. 107–110) : son usage en production est **[abs]**, et `tokensInUsd` ne contient aucun WETH. Une série comparant Pyth à la médiane de places hors Pyth n'existe pas dans la pile de Hylo [abs]. Elle servirait à **calibrer** deux bornes que Hylo règle en état on-chain (intervalle 1–60 s, tolérance de confiance ≤ 5 %, valeurs actives non lues).
2. **Une carte des racines derrière le feed unique.** Hylo ne peut pas détecter une divergence de sources, puisqu'il n'en a qu'une. Savoir si les éditeurs de Pyth pour BTC/ETH/SOL sont les mêmes places que celles d'un éventuel second oracle (Chainlink, RedStone) est précisément la question R2. Cela dirait si un second oracle partage des amonts nommés avec Pyth (recouvrement constaté ou non sur l'axe des places) ; l'indépendance n'en serait pas établie. La liste des places derrière chaque flux Pyth **n'est pas sur les pages lues** [abs].
3. **Le contrôle de parité USDC.** Il bloque les routes quand l'écart à 1 $ dépasse la tolérance configurée, au plus 0,001 $. Shōgen peut dire, sur ses fenêtres calmes, combien de fois des places réelles s'écartent de 10 points de base, et si un écart de Pyth coïncide avec celui d'une place nommée (co-occurrence, sans attribution ; les stables en période calme diront surtout qu'il n'y a rien à signaler : `SYNTHESE-CROISEMENT.md`, question 4).
4. **Hors périmètre actuel** : SOL et HYPE, qui portent l'essentiel des garanties de Hylo (SOL et LST ≈ 90 % du TVL, §1.2), ne sont pas dans S2-bis. Les couvrir serait une extension, avec une classe par actif. HYPE est un cas particulier : Hyperliquid indique que, pour HYPE, son propre oracle n'inclut pas de sources externes “until sufficient liquidity is met” (`pages2/hl-oracle.txt`), donc les amonts nommés derrière Pyth HYPE/USD sont à établir ; leur profondeur n'est pas mesurée par Shōgen [lu pour la phrase Hyperliquid, inféré pour le lien].
5. **Le risque cbBTC/BTC n'est pas dans l'oracle** : le pool BTC est valorisé par Pyth BTC/USD, alors que la garantie est du cbBTC : un décrochage cbBTC/BTC ne se voit pas dans ce prix [lu pour la valorisation, inféré pour la conséquence]. Hors S2-bis.
6. **Veille de régime** : la mise à niveau de Pyth Core (2026-08-26, 3/5 routeurs) change la racine technique de tous les consommateurs. Cette date est un point de rupture à documenter pour toute série de comparaison qui chevauche le 2026-08-26 [inféré].
7. **Limite honnête** : rien de tout cela n'aurait détecté les incidents de §3 qui tiennent à une clé, à une configuration ou à une fermeture de fournisseur (voir §3.3).

Audits Scope : Sec3 (16 déc. 2024), OtterSec (16 déc. 2023), Offside Labs (8 déc. 2023), tels qu'écrits sur la page (l'ordre chronologique est inhabituel mais c'est ce que la page affiche) [lu]. Revendications propres, non recoupées : les cartes de la page affichent “0 Oracle Exploits” et “$19.33B Volume” [lu, déclaratif].

### 2.2 Jupiter — Lend, JupUSD, Perps (Solana)
- **Jupiter Lend** (`jup-lend-oracles.txt`, https://developers.jup.ag/docs/lend/oracles) : “The system computes exchange rates by processing prices from up to four sources in a sequential chain.” Types de sources : Pyth push, Chainlink, RedStone, pools de mise en jeu (Jito, Marinade…), pools à validateur unique (SinglePool), taux de JupLend. Fraîcheur maximale : **600 s** pour les opérations utilisateur, **7 200 s** pour les liquidations ; confiance : 2 % (opérations) et 4 % (liquidations) du prix, mais “Only Pyth validates confidence.” Fournisseurs : Pyth pour SOL, ETH, BTC, JLP ; Chainlink pour SOL/USD, WBTC/USD, EURC/USD [lu]. Audité par Zenith et Offside (même page) [lu]. Taille : **1,318 Md$** (emprunts 988 M$) [lu].
- **JupUSD** (stablecoin adossé à USDC ou USDtb, `jupusd.txt`) : le programme utilise des flux de Pyth, Chainlink et Chaos Labs (“The JupUSD program uses oracle price feeds from” suivi de la liste) pour valider la parité du collatéral et calculer le taux. “There is no fallback mechanism.” Si Pyth est indisponible ou rejeté, la transaction échoue (`PriceConfidenceTooWide`, `NoValidPrice`) [lu]. Seuls des participants KYC/KYB peuvent créer ou racheter ; le public passe par Jupiter Swap [lu]. Circulation : **48,96 M$**, classé crypto-backed (DefiLlama) [lu]. Le guide du SDK précise : “Each vault requires a specific set of Pyth oracle accounts” (même page) [lu].
- **Jupiter Perps / JLP** (`jup-dev-llms.txt`, `jup-perps-custody.txt`) : le pool détient SOL, ETH, BTC, USDC, USDT et JupUSD : “The Custody account stores parameters and state for each token (SOL, ETH, BTC, USDC, USDT, JupUSD) managed by the JLP pool” (index développeurs). **Les pages lues ne décrivent pas la source de prix des perps** : le champ `oracle` est cité sans détail **[abs]**. TVL 820 M$ (emprunts 149 M$) [lu]. Le paramètre de financement est réglé avec Gauntlet et Chaos Labs (`jup-perps-custody.txt`) [lu].
- **Shōgen** : le pool JLP détient précisément **BTC, ETH, USDC, USDT** (plus SOL) : les quatre actifs de S2-bis. C'est un candidat naturel pour un observatoire R1/R2, mais sa source de prix n'a pas été lue **[inféré]**.

### 2.3 Drift, puis Velocity — Solana, contrats perpétuels (`pages2/velocity-*.txt`, `drift-llms.txt`)
- **Contexte** : Drift a subi le **2026-04-01** une perte de 285 M$ (rapport tiers, §3.1). La doc Velocity indique : “Velocity Protocol is a fork of Drift Protocol v2” (`velocity-migrate.txt`) et “The Drift program is paused” ; l'index `drift-llms.txt` copié depuis le site Drift contient en fait les pages **Velocity** (titre Velocity Protocol) : la doc de Drift avant l'incident ne m'est pas parvenue **[abs]**.
- **Sources (Velocity)** : “Two sources are supported: Pyth Lazer and Pyth push.” et “The Switchboard and Pyth pull variants are deprecated and rejected onchain.” (`velocity-oracles.txt`). Source fixée marché par marché. Un oracle de prélancement est **auto-référent** (le prix est la TWAP du marché lui-même, bornée par l'admin) et la page note qu'un tel marché a “no outside anchor” [lu].
- **Panne ou divergence** : six grades classent chaque lecture : non positif ; trop volatil (×5 ou ÷5 face à la TWAP) ; trop incertain (2 % du prix × multiplicateur de palier) ; périmé pour la marge (**48 s**, 144 s pour les stables) ; données insuffisantes (Pyth push) ; périmé pour l'AMM (**4 s**). Chaque action accepte des grades différents : à 10 s sans mise à jour l'AMM cesse de coter ; à 50 s les marges et fills s'arrêtent mais la page précise que liquidations et ordres déclencheurs continuent (“liquidation and trigger orders still run”) [lu].
- **Taille** : Drift Trade 0,64 M$ (DefiLlama) ; Velocity figure sans valeur de TVL, parent Drift [lu].
- **Shōgen** : la grille à six grades est la plus fine description publique d'un traitement de panne d'oracle que j'aie lue ; elle est reprenable comme vocabulaire pour la partie staleness et panne de Shōgen **[inféré]**.

### 2.4 Hyperliquid — L1 propre, perps et marchés HIP-3 (`pages2/hl-*.txt`)
- **Source du prix (HyperCore)** : les validateurs publient un prix spot d'oracle pour chaque actif toutes les 3 secondes, “weighted median of Binance, OKX, Bybit, Kraken, Kucoin, Gate IO, MEXC, and Hyperliquid spot mid prices for each asset”, poids 3, 2, 2, 1, 1, 1, 1, 1 ; le prix final est “where the validators are weighted by their stake” (médiane pondérée par la mise des prix des validateurs) (`hl-oracle.txt`). Pour les actifs dont la liquidité spot principale est hors Hyperliquid (BTC cité), le spot Hyperliquid n'entre pas ; pour ceux dont elle est sur Hyperliquid (HYPE cité), les sources externes ne sont pas utilisées “until sufficient liquidity is met” [lu]. Ce prix sert au financement et entre dans le prix de marque (marge, liquidations, ordres déclencheurs) (même page) [lu].
- **Marchés HIP-3** (`hl-hip3.txt`) : le déployeur d'un marché est responsable de la définition du marché et de son exploitation, c'est-à-dire de “setting oracle prices, leverage limits, and settling the market if needed” ; stake de 500 k HYPE, maintenu au moins 183 jours après le déploiement du dex (“maintained for a minimum of 183 days after the dex is deployed”) ; **slashing** par vote des validateurs ; marge croisée seulement pour les actifs ayant “a reliable external oracle source” et un examen si `externalPerpPx` bouge de plus de 50 % dans la journée [lu].
- **Panne ou divergence** : le texte ne décrit pas de bascule entre sources ; la médiane pondérée absorbe un écart de place **[inféré]** ; aucune page lue n'indique le comportement si une place s'arrête **[abs]**.
- **Taille** : Hyperliquid Bridge **7,13 Md$** ; HLP 181,6 M$ ; carnet spot 178,6 M$ (DefiLlama) [lu] (l'entrée Hyperliquid Perps est sans valeur de TVL dans DefiLlama).
- **Incidents** : JELLY (2025-03-26) et POPCAT (2025-11-12), §3.1 ; la source de POPCAT ne mentionne aucun oracle, le lien est [inféré].
- **Shōgen** : le poids de Binance (3 sur 11, soit environ 27 %, pour un actif comme BTC dont le spot Hyperliquid est exclu : “do not include Hyperliquid spot prices in the oracle” ; 3 sur 12, soit 25 %, si le spot Hyperliquid est inclus) et la présence de Kraken sont lisibles : Hyperliquid est lui-même un agrégateur dont les racines sont des places de S2-bis **[inféré]**. `SYNTHESE-CROISEMENT.md` (ligne 124) note un désaccord interne sur le champ à lire (`midPx` ou `oraclePx`), que cette fiche ne tranche pas.
