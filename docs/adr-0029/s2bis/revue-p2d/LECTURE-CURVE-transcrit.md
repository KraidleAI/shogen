## Point 1. Sémantique de `get_dy(i, j, dx)`

### 1a. Pool Stableswap-NG (ex. pool `0x4f493B7d…`)
- Définition : “Function to calculate the predicted output amount `j` to receive at the pool's current state given an input of `dx` amount of coin `i`.” `https://docs.curve.finance/developer/amm/stableswap-ng/pools/plainpool.md` (section `get_dy`) [lu, 2026-10-17]. Fichier : `pages/docs.curve.finance_developer_amm_stableswap-ng_pools_plainpool.md`.
- Frais inclus : le code publié par la page soustrait le frais avant de rendre : “return (dy - fee) * PRECISION / rates[j]” (même page, vue `CurveStableSwapNGViews`) [lu]. Le frais est dynamique : “fee: uint256 = self._dynamic_fee((xp[i] + x) / 2, (xp[j] + y) / 2, base_fee, fee_multiplier) * dy / FEE_DENOMINATOR” (même page) [lu]. La page cite aussi le glissement : le calcul passe par `get_y` avec le nouveau solde, donc la sortie est nette de frais et de glissement [lu, code de la même page].
- Unités d'entrée et de sortie : `dx` et le résultat sont dans les unités natives des coins `i` et `j`. Preuve de la page de la fabrique : “_rate_multipliers.append(10 **(36 - decimals[i]))” (`https://docs.curve.finance/developer/amm/factory/stableswap-ng/overview.md`, `deploy_plain_pool`) [lu] ; avec ce multiplicateur, `dx * rates[i] / PRECISION` met l'entrée à l'échelle 18 décimales et la division finale par `rates[j]` ramène la sortie aux décimales de `j` [inféré par lecture du code publié]. Exemple de la doc : `StableSwap.get_dy(0, 1, 10**18)` rend `999712` (coin 1 à 6 décimales) [lu, exemple de la page].
- Index : “Index values can be found via the `coins` public getter method” (même page) [lu].

### 1b. 3pool (ancien contrat Vyper) `0xbEbc44782C7dB0a1A60Cb6fe97d0b483032FF1C7`
- Aucune page de la documentation ne décrit `get_dy` du 3pool nommément. La doc des pools “plain” anciens (dont le 3pool est cité en exemple : “An example of a Curve plain pool is [3Pool]”) dit : “Get the amount of coin `j` one would receive for swapping `dx` of coin `i`.” `https://docs.curve.finance/developer/amm/legacy/stableswap/pools/plain-pools.md` [lu]. Même page, exemple cité pour le pool EURS, pas pour le 3pool.
- Avertissement de la doc : “Please **do not**assume for a Curve pool to implement the API outlined in this section but verify this before interacting with a pool contract.” `https://docs.curve.finance/developer/amm/legacy/stableswap/pools/overview.md` [lu].
- Source du contrat du 3pool, dépôt officiel `curvefi/curve-contract`, `https://raw.githubusercontent.com/curvefi/curve-contract/master/contracts/pools/3pool/StableSwap3Pool.vy` [lu] :
  - “# dx and dy in c-units” ;
  - “dy: uint256 = (xp[j] - y - 1) * PRECISION / rates[j]” ;
  - “_fee: uint256 = self.fee * dy / FEE_DENOMINATOR” puis “return dy - _fee” : frais inclus, sortie en unités natives de `j` (avec “RATES: constant(uint256[N_COINS]) = [1000000000000000000, 1000000000000000000000000000000, 1000000000000000000000000000000]” : DAI 18 décimales, USDC et USDT 6 décimales [inféré : 10^18 / 10^30 = 10^(36 - décimales)]).
  - Frais plat (non dynamique), contrairement au NG.
- Adresse : README du 3pool du même dépôt : “[0xbebc44782c7db0a1a60cb6fe97d0b483032ff1c7]” rattaché à `StableSwap3Pool` (`https://raw.githubusercontent.com/curvefi/curve-contract/master/contracts/pools/3pool/README.md`) [lu] ; même adresse que `0xbEbc44782C7dB0a1A60Cb6fe97d0b483032FF1C7` à la casse près [inféré par comparaison]. Décimales du 3pool dans l'API officielle : DAI 18, USDC 6, USDT 6 (champ `decimals`) [lu, `api.curve.finance`].
- Limite : que le fichier `master` du dépôt soit identique au bytecode déployé n'est pas vérifié (Etherscan non lu, historique git du dépôt non lu) [abs].

## Point 2. Dénominateur des frais

- 3pool : “FEE_DENOMINATOR: constant(uint256) = 10 ** 10” et “fee: public(uint256)  # fee * 1e10” (`StableSwap3Pool.vy`, URL du point 1b) [lu]. Donc `fee()` brut se lit sur 10^10. Avec la valeur brute 1 500 000 relevée par la passe précédente (`PAIRES-ET-TEMOIN.md` §3.1, [2nd] pour moi : je n'ai fait aucun appel), 1 500 000 / 10^10 = 0,015 % [inféré, arithmétique].
- Pools NG : “FEE_DENOMINATOR: constant(uint256) = 10 **10” (`https://docs.curve.finance/developer/amm/factory/stableswap-ng/overview.md`, constantes de la fabrique) [lu]. La page du pool NG utilise `FEE_DENOMINATOR` sans afficher sa définition [abs] ; l'égalité avec la constante de la fabrique pour le pool est [inféré]. Avec la valeur brute 100 000 de la passe précédente [2nd], 100 000 / 10^10 = 0,001 % [inféré, arithmétique]. Pour le NG, `fee()` n'est que la base : le frais appliqué est dynamique (point 1a), `offpeg_fee_multiplier()` non relevé [abs].

## Point 3. Sens de `price_oracle`

Page : `https://docs.curve.finance/developer/amm/stableswap-ng/pools/oracles.md` [lu, 2026-10-17].
- Nature : “An exponential moving-average price oracle of an asset within the AMM with regard to the coin at index 0.” [lu].
- Signature et indice : “Function to calculate the exponential moving average (EMA) price for the coin at index `i` with regard to the coin at index 0.” ; “`i = 0` will return the price oracle of `coin[1]`, `i = 1` the price oracle of `coin[2]`, and so on.” [lu]. (Le paramètre est donc l'indice décalé : `price_oracle(0)` = prix du coin 1 exprimé en coin 0.)
- Pour un pool à deux coins USDC (indice 0) / USDT (indice 1) : `price_oracle(0)` = prix de USDT en USDC [inféré par application de la règle ci-dessus ; la page ne traite pas ce pool].
- Unités : exemple de la page : “>>> price_oracle() = 999043303185591283” suivi de “0.99904330318       # price of crvUSD w.r.t USDC” : entier à 18 décimales, quel que soit le nombre de décimales des coins [lu, exemple de la page ; coin 0 de l'exemple = USDC à 6 décimales]. Prix inverse : la page donne 10^36 / `price_oracle()` (formule LaTeX de la page) [lu].
- EMA, fenêtre `ma_exp_time` : “`ema_price` is maximally updated once per block” (même page) [lu] ; le prix au dernier relevé est la dernière valeur spot de l'AMM, non le prix d'un échange simulé ; ce n'est pas une sortie nette de frais [inféré].
- Avertissement : le bogue d'oracle ne touche que les pools déployés avant une date : “Pools deployed after **`Dec-12-2023 09:39:35 AM +UTC`** do not include the bug” [lu] ; il porte sur des jetons de décimales ≠ 18 ou à taux externes, via `remove_liquidity_imbalance`, et ne touche pas les échanges [lu, même page]. Le pool `0x4f493B7d…` a `creationTs` 1737825647 dans l'API (`date -u -d @1737825647` : 2025-01-25 17:20:47 UTC), postérieur à la date de correction [lu + inféré] ; que sa mise en oeuvre soit celle corrigée n'est pas relevé sur chaîne [abs].

## Point 4. Rattachement du pool `0x4f493B7d…` à la fabrique Stableswap-NG

- API officielle `https://api.curve.finance/v1/getPools/all/ethereum` (fichier `pages/api.curve.finance_v1_getPools_all_ethereum.json`, `generatedTimeMs` 1792232008370) [lu] : entrée d'adresse `0x4f493B7dE8aAC7d55F71853688b1F7C8F0243C85`, champs affichés : `"id": "factory-stable-ng-355"`, `"implementation": "plainstableng"`, `"registryId": "factory-stable-ng"`, `"factory": true`, `"name": "Curve.fi Strategic USD Reserves"`, décimales 6 et 6, coins USDC puis USDT. Le même pool figure dans `https://api.curve.finance/v1/getPools/ethereum/factory-stable-ng` (1075 pools dans ce registre) [lu]. L'OpenAPI de l'API décrit `/getPools/{blockchainId}/{registryId}` ainsi : “Returns information on all pools, in a specific registry, on a specific chain.” [lu] ; `factory-stable-ng` est une valeur de l'énumération `registryId` [lu].
- Fabrique NG de la doc : `https://docs.curve.finance/deployments.json`, `ethereum.amm.stableswap.factory` = `0x6A8cbed756804B16E05E741eDaBd5cB544AE21bf`, `plain-amm-implementation` = `0xDCc91f930b42619377C200BA05b7513f2958b202` ; le fichier se déclare : “This is the source of truth for deployment data in this checkout.” [lu].
- Recoupement : l'API donne pour ce pool `"implementationAddress": "0xDCc91f930b42619377C200BA05b7513f2958b202"`, identique à `plain-amm-implementation` de la fabrique de `deployments.json` [lu, deux pièces ; l'identité est ma comparaison, [inféré]]. 1022 des 1075 pools du registre portent cette même implémentation (comptage de mon script sur le fichier sauvegardé).
- Ce qui manque : l'API n'affiche pas l'adresse de la fabrique parente d'un pool (le champ `factory` vaut `true`, sans adresse) [abs] ; la doc ne publie pas de liste de pools de la fabrique (`pool_list` est un getter de contrat, non appelé : interdit) [abs]. Le rattachement direct pool → `0x6A8cbed7…` n'est donc pas lu ; il est établi seulement par le registre officiel `factory-stable-ng` et l'implémentation commune [2 pièces officielles lues, rattachement [inféré]]. Une implémentation clonée hors fabrique aurait la même adresse d'implémentation : l'identité d'implémentation ne prouve pas à elle seule le rattachement.

## Conclusion pour le codeur de CB-9 (trois lignes)

Appeler `get_dy(i, j, dx)` (view) avec `dx` dans les unités natives du coin `i` (10^6 pour 1 USDC) : la sortie est dans les unités natives de `j` (6 décimales USDT), nette de frais (plats pour le 3pool, dynamiques pour le NG) et de glissement ; prix = sortie / 10^6 pour une entrée de 10^6 ; `price_oracle(0)` du NG = EMA à 18 décimales du prix du coin 1 en coin 0, ni net de frais ni échange simulé.

Limites à déclarer : doc de `get_dy` du 3pool = doc générique des pools plain anciens + source `master` du dépôt (identité avec le bytecode déployé non vérifiée) ; rattachement direct du pool NG à la fabrique non lu (registre API `factory-stable-ng` + implémentation commune seulement) ; absence de bogue d'oracle du pool NG non vérifiée sur chaîne.
