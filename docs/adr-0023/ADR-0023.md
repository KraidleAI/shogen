# ADR-0023 — Perte de la source Pyth en campagne S2 (Hermes public gaté par clé) : acceptation de `oracle_pyth` absent, invariant « sans clé » préservé

- **Statut** : proposé — décision orchestrateur sous mandat investisseur, advisor consulté AVANT décision. **Aucun changement de code, aucune clé, aucun redémarrage** → pas de gate G2/oracle requise ; acceptation investisseur puis commit orchestrateur (R-19/R-20).
- **Date** : 2026-09-03.
- **Rattachement** : RUNBOOK-campagne §1 (« **strictement sans clé — aucune clé, aucun token, aucun cookie** »), ADR-0020 (`run_params` ex ante, fail-closed), ADR-0021/ADR-0022 (σ/τ par classe : `oracle_pyth` τ=0,15 %, σ=33 s), doc 04 (diversité mesurée, k_eff), doc 10 §3.1 (les 11 sources / 12 flux), ADR-0003 (recalculabilité).
- **Mandat** : décision déléguée par l'investisseur — « **fais le nécessaire et consulte l'advisor avant de décider** » (2026-09-03).

## Contexte — l'événement (faits vérifiés)

1. **Cause racine [lu] primaire** (docs.pyth.network/price-feeds/core/fetch-price-updates, fetch 2026-09-03) : « **Pyth Core was upgraded on August 26, 2026** » et « **Hermes now requires an API Key** » (`Authorization: Bearer $PYTH_API_KEY` ; endpoint `pyth.dourolabs.app/hermes`). **Aucun endpoint public sans clé n'est documenté.**
2. **Observation, recalculable depuis les journaux** : le flux Pyth de la campagne (`sources.py:271-275`, Hermes `hermes.pyth.network/v2/updates/price/latest?ids[]=0xe62df6…415b43&parsed=true`) renvoie **HTTP 401** dès la **1ʳᵉ fenêtre (2026-08-26 20:00 UTC)** — **8 144 `panne_http` / 8 146 fenêtres ≈ 100 %**. En **calibration** (21→23/08, AVANT l'upgrade), Pyth répondait http 200 (`calibration/journal.jsonl`). Vérif live directe 2026-09-03 : WebFetch de l'URL exacte → **401 Unauthorized**.
3. **Réconciliation chronologique** : le basculement a eu lieu le **26/08** (upgrade Pyth Core = jour de lancement de la campagne), **pas le 18/08** (date d'un snippet WebSearch non primaire, écartée) — cohérent avec le 401 dès la fenêtre 1.
4. **Le harnais a fail-closed CORRECTEMENT** : `status=panne_http`, `price=null`, **aucune valeur inventée** (`test_sources.py` : « un corps illisible devient une panne, jamais une valeur inventée »). La classe `oracle_pyth` a **0 donnée de campagne**.

## Décision

**A — accepter `oracle_pyth` absent pour toute la campagne S2. Ne rien changer de live : aucune clé, aucun changement d'endpoint, aucun redémarrage.**

Fondement (la décision découle du **design**, ce n'est pas une dégradation subie) :
- Le RUNBOOK §1 fige un **invariant de conception : « strictement sans clé »** — la thèse Shōgen est la **recalculabilité par quiconque, sans accès privilégié**. Pyth exige désormais une clé **sans alternative keyless** → **restaurer Pyth violerait l'invariant**. L'invariant tranche : B/C/D sont exclus par le design lui-même.
- Le fail-closed est le **comportement VOULU** : une source qui devient inaccessible en pleine campagne est **exactement l'événement d'attestation que la méthode est bâtie pour survivre** — elle l'a loggé, datée, jamais comblé. **C'est un résultat, pas une excuse.**

## Conséquences

1. **La campagne continue inchangée** sur **10 sources / 11 flux** (Pyth retiré de fait). Aucune action live.
2. **`oracle_pyth` = vide** dans la table §6 et les rapports **J14 (~4 sept) / J28 (18 sept)** — **documenté, jamais un blanc silencieux** ; note de résidu au rapport.
3. **Diversité mesurée** : k nominal −1 ; **k_eff recalculé sur les sources réellement présentes** (le cadre gère un k variable ; RUNBOOK §6 « harnais-down ≠ source-en-panne », les pannes se journalisent, ne se corrigent pas en silence). Le drapeau 2 / la matrice φ n'utilisent que les sources présentes.
4. **ADR-0022 τ_pyth (0,15 %) et σ_pyth (33 s) restent committés** (recalculabilité) mais **non exercés** (aucune donnée `oracle_pyth`).
5. **Aucune rupture ADR-0003** : rien n'est modifié dans le binaire d'analyse épinglé.

## Alternatives écartées

- **B — restaurer via un endpoint public keyless** : **aucun n'existe** (docs Pyth [lu]) → B s'effondre.
- **B′ — lecture Pyth on-chain via RPC public** (Pythnet/EVM) : nouveau décodeur + nouveau code **sur un harnais gelé en plein run** = trop risqué (avis advisor) ; **noté pour une campagne future**, hors périmètre ici.
- **C — relancer la campagne** : perd ~9 j de bonnes données 10-sources, et Pyth resterait inaccessible sans clé → **ne résout rien**.
- **D — clé provider (Bearer)** : **VIOLE l'invariant « strictement sans clé »** (RUNBOOK §1) ; l'investisseur ne fournit pas de clé et l'orchestrateur ne manipule pas de credentials (règle de sécurité). Rejeté par le design.

## Note prospective (non bloquante)

Pour une **campagne future**, si Pyth est jugé nécessaire : deux voies **hors invariant keyless** (clé provider, ou lecture on-chain via RPC) — décision investisseur explicite requise, contre le principe « sans clé ». À rappeler par ailleurs (mémoire 2026-08-19, Chaos Labs) : **les publishers Pyth ne sont pas vérifiables par un tiers sur Pythnet** — la valeur probante de Pyth comme source *attestée* était déjà limitée, ce qui affaiblit l'argument de le restaurer à tout prix.
