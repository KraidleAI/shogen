# Survivants justifiés du score de mutation du cœur — ADR-0011 seuil 3.
#
# Forme : <mutant, exactement comme `mutants.out/missed.txt` l'écrit> # <justification en une ligne>
#
# Ce fichier est la LIGNE DE BASE de la non-régression : `cargo xtask mutation`
# casse sur tout survivant qui n'y figure pas. Il n'est pas une liste
# d'exemptions — chaque ligne porte la DÉMONSTRATION que le mutant est
# équivalent au programme, au sens de Jia & Harman p. 4 : aucune entrée du
# programme ne distingue le mutant de l'original. « Automatically detecting all
# equivalent mutants is impossible » (§II.B, p. 4) : c'est un travail humain, et
# c'est ici qu'il est écrit.
#
# Un survivant TUABLE n'a rien à faire ici : il se tue par un test, dans
# `crates/shogen-core/tests/mutation_programme.rs`. Quatorze l'ont été le
# 2026-08-13, sur les 34 survivants de la PREMIÈRE mesure (417 générés,
# 351 tués, 34 survivants, 32 non viables — score 91,1688 % ; trace : le
# rapport du chantier G au JOURNAL du 2026-08-13). Cette première mesure
# était NON REJOUABLE — la course du répertoire temporaire à chemin fixe,
# décrite plus bas, faisait basculer des issues d'un run à l'autre — donc
# 34 − 14 ne DOIT PAS se réconcilier arithmétiquement avec les 22 lignes
# ci-dessous : la population de survivants a bougé entre les deux mesures
# (exemple tracé : subject.rs:522:17, compté survivant au premier run, tué
# au second). Seul l'état re-mesuré après le correctif fait foi (revue G2
# vague 1 : un chiffre qui ne se rattache pas à sa mesure ne se copie pas).
#
# ÉTAT MESURÉ ET REJOUABLE — **vague 2, chantier de corrections de la revue
# G2, 2026-08-13** (`cargo xtask mutation`, cargo-mutants 27.1.0,
# parallélisme 4) : **426 mutants générés, 372 tués, 22 survivants, 32 non
# viables — score 94,4162 % sur 394 non équivalents**. Les 22 survivants sont
# EXACTEMENT les 22 lignes ci-dessous.
#
# Ce chiffre est, au dernier chiffre, celui de la mesure précédente du même
# jour : les deux correctifs du cœur de ce chantier — le refus du caractère de
# contrôle dans `controler_identifiant` (`temoignage_canonique.rs`) et le refus
# de l'`attestor` vide avant le contrôle (f) (`verification.rs`) — n'ont fait
# naître **aucun** mutant nouveau. Les deux sont des appels de méthode gardant
# un `return Err(...)` : `cargo-mutants` ne les mute pas, la population reste
# 426 (comptée à l'exécution, pas déduite).
#
# Ce que ce chantier a changé, et pourquoi les numéros de ligne de `subject.rs`
# ont encore bougé, de +8 cette fois : la doc de `hote_de_subject` a été
# corrigée (mineure A5 de la revue — elle promettait « chaîne vide sur entrée
# hors forme » alors que le repli ne couvre que l'absence de préfixe), et le
# texte plus long a décalé le fichier de 8 lignes. Les NEUF entrées de
# `subject.rs` ci-dessous sont les mêmes mutants, aux mêmes justifications, au
# nouveau rang : 327→335, 361→369, 501→509, 537→545, 543→551 (trois entrées),
# 590→598, 603→611 — décalage constant, vérifié entrée par entrée contre la
# liste mesurée. Le run qui a rendu ROUGE ne signalait QUE ces neuf-là, et
# aucun survivant hors ligne de base : un décalage de fichier n'est pas une
# régression, et la gate le dit en refusant tant que la ligne de base n'est
# pas recalée.
#
# Ce que la vague 2 avait déjà changé, plus tôt le même jour : les numéros de
# `subject.rs` avaient bougé de +21 à l'ajout de `hote_de_subject` (l'alinéa
# (h), ADR-0015 point 17). Ce décalage-là est absorbé dans les rangs
# ci-dessous, au même titre que le +8 du chantier de corrections. (Les numéros
# cités dans le commentaire historique plus haut, eux, ne se recalent pas :
# ils tracent une mesure passée, pas la ligne de base.)
#
# La même mesure a fait naître QUATRE survivants sur `rendu_de_cle`
# (`verification.rs`, contrôle (f)) : ils étaient **tuables**, ils ont été
# **tués** par trois tests de `mutation_programme.rs` — un survivant tuable n'a
# rien à faire ici. Ce qu'ils montraient : aucune suite n'imprimait le refus
# d'épinglage, alors que ce refus est le seul endroit où un tiers lit quelle
# clé a été épinglée et quelle clé a servi.
#
# ÉTAT PRÉCÉDENT (vague 1, même jour) : 417 mutants générés, 363 tués, 22
# survivants, 32 non viables — score 94,2857 % sur 385 non équivalents.
#
# Pourquoi « rejouable » est écrit ici. Les trois premières mesures de la
# journée ne l'étaient pas : le même mutant était compté survivant dans l'une
# et tué dans l'autre. La cause a été trouvée sur pièce — les tests de bout en
# bout du vérificateur travaillaient dans un répertoire temporaire au chemin
# FIXE, que chacun efface en entrant ; sous les quatre suites de front de cette
# gate, un processus effaçait les lots d'un autre. Le chemin porte désormais le
# PID (`crates/shogen-verifier/tests/`), et le run de re-mesure rend une liste
# de survivants IDENTIQUE à cette ligne de base (22 sur 22, zéro entrée non
# revue) — ce qui est un run, pas une série : ce qui porte la stabilité ici
# est le mécanisme retiré, pas le compte de répétitions. Un score
# non rejouable n'est pas un fait (ADR-0011 point 2) : la liste ci-dessous
# n'aurait rien valu tant que cette course existait.
#
# Trois équivalences seulement sont vraies « en soi » (les identités de FIPS
# 180-4). Les autres sont équivalentes AU PROGRAMME : la fonction mutée se
# comporterait différemment sur une entrée que rien, dans ce dépôt, ne lui
# donne. La distinction est écrite ligne à ligne, parce qu'elle change ce qui
# invaliderait la justification : un site d'appel nouveau, et non un test
# nouveau.
